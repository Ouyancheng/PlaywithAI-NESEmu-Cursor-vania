# TestAiNES Emulator Modules

This document explains how the emulator is organized and how the major pieces work together. TestAiNES is split into a portable C++20 emulation core plus native platform frontends.

## High-Level Flow

The main runtime path is:

1. The macOS app loads a `.nes` ROM through `Nes::loadRom()`.
2. `Cartridge` parses the iNES header, stores PRG/CHR data, and creates the mapper.
3. `Nes::stepFrame()` clocks the system until the PPU reports a completed frame.
4. The PPU publishes a completed framebuffer.
5. The active frontend uploads a locked framebuffer snapshot and presents it.
6. Audio samples generated by the APU are pushed to the platform audio backend.

The core keeps CPU, PPU, APU, cartridge, mapper, and controller behavior separate. The `Bus` is the central wiring point that routes CPU reads/writes to the right hardware component.

## Core Types

Files:

- `src/core/Types.hpp`

This file defines the shared integer aliases (`u8`, `u16`, `u32`, `u64`), NTSC constants, NES screen dimensions, `Rgb`, and `Framebuffer`.

The framebuffer is a fixed-size `std::array<Rgb, 256 * 240>`, matching the NES visible resolution.

## Emulator Facade

Files:

- `src/core/Nes.hpp`
- `src/core/Nes.cpp`

`Nes` is the public core facade used by the macOS app and tests. It owns:

- `Bus`
- `CPU6502`
- `Cartridge`
- Pending NMI/IRQ latches
- A mutex protecting frontend access to frame and input state

Important responsibilities:

- Load ROMs and attach the cartridge to the bus.
- Reset all core state.
- Step exactly one frame by clocking the PPU three times per CPU cycle and the CPU/APU/mapper once per CPU cycle.
- Latch NMI/IRQ requests and deliver them only between CPU instructions.
- Expose controller input.
- Return a framebuffer snapshot for the GUI.

The framebuffer snapshot exists because the macOS view and emulation timer can run independently. The GUI must not upload from a live framebuffer while the emulator is publishing a new completed frame.

## CPU

Files:

- `src/core/CPU6502.hpp`
- `src/core/CPU6502.cpp`

`CPU6502` implements the NES CPU instruction executor, addressing modes, registers, stack behavior, flags, interrupts, and cycle accounting.

Implemented behavior includes:

- Official 6502 instructions used by NES software.
- Common unofficial opcodes used by commercial games and diagnostics.
- Addressing modes including zero page, absolute, indexed, indirect, and the 6502 indirect JMP page-wrap bug.
- NMI and IRQ entry.
- `RTI`, `BRK`, stack pushes/pulls, and interrupt-disable flag behavior.

Important detail: interrupt entry must push the old processor status before setting the interrupt-disable flag. If the emulator pushes status after setting `I`, `RTI` restores the wrong flag state and mapper IRQs can stop firing.

## Bus

Files:

- `src/core/Bus.hpp`
- `src/core/Bus.cpp`

The `Bus` connects the CPU address space to hardware:

- `$0000-$1FFF`: 2 KB internal RAM mirrored every `$0800`.
- `$2000-$3FFF`: PPU registers mirrored every 8 bytes.
- `$4000-$4017`: APU, controller, and DMA registers.
- Cartridge PRG space through the active mapper.

The bus also implements OAM DMA through `$4014`. During DMA, 256 bytes are copied into PPU OAM and the CPU is stalled for the DMA duration while PPU/APU/mapper devices continue clocking.

## PPU

Files:

- `src/core/PPU.hpp`
- `src/core/PPU.cpp`

The PPU is responsible for video timing, scroll state, nametable/palette memory, background fetches, sprite evaluation, and frame publishing.

Important implemented areas:

- PPU register interface: `PPUCTRL`, `PPUMASK`, `PPUSTATUS`, `OAMADDR`, `OAMDATA`, `PPUSCROLL`, `PPUADDR`, `PPUDATA`.
- Loopy scroll registers (`v`, `t`, `x`, `w`) through `vramAddress_`, `tramAddress_`, `fineX_`, and `writeLatch_`.
- Background tile fetch pipeline with pattern and attribute shifters.
- Coarse X/Y increments and horizontal/vertical scroll transfers at PPU-compatible dots.
- Nametable mirroring through the cartridge mapper.
- Palette mirroring and grayscale masking.
- Sprite scanline selection, sprite rendering, sprite-zero hit, and sprite overflow approximation.
- Odd-frame cycle skip when rendering is enabled.
- Back-buffered rendering: pixels are drawn into `renderFramebuffer_`, then copied to `framebuffer_` at vblank.

The PPU renders into a back buffer because frontend code should only see complete frames. The GUI additionally takes a locked snapshot to avoid reading while the core is publishing a frame.

## APU

Files:

- `src/core/APU.hpp`
- `src/core/APU.cpp`

The APU generates NES audio samples. It currently models:

- Two pulse channels with envelopes, length counters, and sweep behavior.
- Triangle channel with linear counter and length counter.
- Noise channel with envelope and LFSR mode.
- Frame counter timing for quarter-frame and half-frame updates.
- DMC sample fetching, output level stepping, looping, IRQ status, and TND mixer contribution.
- Nonlinear NES-style channel mixing.
- A low-cut DC blocker plus high-frequency-preserving 18 kHz low-pass output stage, with conservative gain balancing to avoid clipping.
- Expansion audio input from mappers such as VRC6.

Audio is clocked once per CPU cycle, not once per PPU cycle. DMC sample fetches are routed through the CPU bus address space so ROM sample data can come from the active cartridge mapping.

## Cartridge

Files:

- `src/core/Cartridge.hpp`
- `src/core/Cartridge.cpp`

`Cartridge` loads iNES ROMs, stores PRG/CHR data, creates the mapper, and delegates CPU/PPU memory operations.

Responsibilities:

- Validate the iNES header.
- Read PRG and CHR ROM sections.
- Allocate CHR RAM when a ROM has no CHR ROM.
- Create the mapper based on the iNES mapper number.
- Report mapper-controlled mirroring.
- Forward IRQ and expansion audio hooks.

Supported mappers:

- Mapper 0: NROM
- Mapper 1: MMC1
- Mapper 2: UxROM
- Mapper 4: MMC3
- Mapper 24: Konami VRC6a
- Mapper 26: Konami VRC6b

## Mapper Interface

Files:

- `src/core/Mapper.hpp`

Mappers translate CPU and PPU addresses into PRG/CHR offsets and may also provide:

- Runtime mirroring mode.
- CPU-clocked IRQ generation.
- Scanline hooks.
- Expansion audio.
- Internal memory handling such as PRG-RAM.

`kMapperHandled` is used when a mapper handled an access internally and the cartridge should not index into PRG/CHR memory.

## NROM

Files:

- `src/core/mappers/NromMapper.hpp`
- `src/core/mappers/NromMapper.cpp`

NROM is the simplest mapper. It provides fixed PRG mapping and direct CHR access. It is useful for basic CPU, PPU, and bus validation.

## UxROM

Files:

- `src/core/mappers/UxromMapper.hpp`
- `src/core/mappers/UxromMapper.cpp`

UxROM is Mapper 2, used by games such as the original NES Castlevania. It provides a switchable 16 KB PRG bank at `$8000-$BFFF`, fixes the last PRG bank at `$C000-$FFFF`, and commonly uses CHR-RAM for pattern data.

## MMC1

Files:

- `src/core/mappers/Mmc1Mapper.hpp`
- `src/core/mappers/Mmc1Mapper.cpp`

MMC1 uses a serial shift register to update control, PRG bank, and CHR bank registers. It supports mapper-controlled mirroring and PRG/CHR banking modes used by many early NES games.

## MMC3

Files:

- `src/core/mappers/Mmc3Mapper.hpp`
- `src/core/mappers/Mmc3Mapper.cpp`

MMC3 provides banked PRG/CHR mapping and IRQ behavior tied to PPU A12 activity. It is required by many later NES games.

## VRC6

Files:

- `src/core/mappers/Vrc6Mapper.hpp`
- `src/core/mappers/Vrc6Mapper.cpp`

VRC6 is the key mapper for Akumajou Densetsu. It includes:

- 16 KB PRG bank at `$8000-$BFFF`.
- 8 KB PRG bank at `$C000-$DFFF`.
- Fixed last 8 KB PRG bank at `$E000-$FFFF`.
- 8 KB PRG-RAM at `$6000-$7FFF`, enabled by `$B003` bit 7.
- Eight CHR bank registers.
- VRC6a/VRC6b register address-line variants.
- Mapper-controlled nametable mirroring.
- VRC IRQ counter and prescaler.
- VRC6 pulse and sawtooth expansion audio channels.

VRC6 is especially sensitive because Akumajou Densetsu uses mapper IRQs to change CHR banks mid-frame. Wrong CPU interrupt status, wrong IRQ timing, wrong mirroring, or wrong frontend frame publishing can all appear as background tile corruption.

## Controllers

Files:

- `src/core/Controller.hpp`

The controller implements NES serial button reads. The frontend sets button state, and CPU reads from `$4016/$4017` shift button bits out according to the strobe state.

## macOS Frontend

Files:

- `src/macos/main.mm`

The app shell uses:

- AppKit for the window, menu, keyboard input, and ROM open panel.
- MetalKit for nearest-neighbor video presentation.
- CoreAudio AudioQueue for sound output.

The frontend runs emulation through an `NSTimer` and renders through `MTKView`. Video upload uses `Nes::framebufferSnapshot()` so Metal never reads from a framebuffer while the emulator is mutating it. AudioQueue output keeps a FIFO of generated samples; if the callback underruns, it ramps from the previous sample when audio resumes instead of jumping abruptly.

## Win32 Frontend

Files:

- `src/win32/main.cpp`

The Windows app shell uses native Win32 APIs:

- Win32 window, menu, timer, keyboard input, and open-file dialog.
- GDI `StretchDIBits` for nearest-neighbor video presentation.
- `waveOut` with 16-bit PCM buffers for audio playback.

The Win32 frontend follows the same high-level model as the macOS frontend: a frame timer advances `Nes::stepFrame()`, pushes APU samples to an audio FIFO, and invalidates the window for repaint. Painting uses `Nes::framebufferSnapshot()` to avoid reading a frame while the emulator is publishing one.

The current development environment is macOS, so Win32 runtime testing needs a Windows machine, Windows VM, GitHub Actions `windows-latest` build, or a MinGW/LLVM-mingw plus Wine workflow.

## Tests

Files:

- `tests/CoreTests.cpp`

The tests are focused smoke and regression tests. They cover:

- CPU execution basics.
- Interrupt status restoration after `RTI`.
- APU frame-counter IRQ behavior and DMC sample fetching.
- Cartridge loading.
- PPU frame completion.
- OAM DMA.
- UxROM PRG bank switching and CHR-RAM.
- VRC6 mirroring, PRG-RAM, Mapper 26 address-line swap, pattern-bank smoke checks, ROM nametable smoke checks, and IRQ behavior.

These tests are not a substitute for full public NES test ROM suites, but they protect the bugs discovered during development.

## Known Remaining Work

The emulator is now playable for the tested Super Mario and Akumajou Densetsu paths, but it is not yet a complete compatibility emulator.

Useful next accuracy targets:

- DMC edge cases and sample-fetch CPU stall timing.
- More exact APU frame counter edge behavior.
- More complete sprite overflow behavior.
- More mapper-specific conformance tests.
- Save RAM persistence.
- NES 2.0 metadata support.
- Broader validation with public CPU, PPU, APU, and mapper test ROMs.
